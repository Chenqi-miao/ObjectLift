## 二、系统架构与模块划分

**可用于汇报的正文：** 系统使用Python业务服务与Gradio工作台，SQLite保存元数据、处理状态和向量，原始媒体与预览文件独立存储。图片和视频统一转成可检索的视觉单元；Jina负责图文向量，Qwen负责描述和标签。应用使用串行模型任务与独立描述进程，控制本地资源竞争。

- 下层：SQLite、托管原文件/预览目录、Jina模型、Qwen独立进程。
- 画出页面调用业务服务、业务服务读写数据的关系；模型下载与日常本地推理分开标注。

## 三、数据建模、导入与持久化

**正文：** 原素材和视觉单元分开建模。一张图片对应一个视觉单元，一段视频对应多个带时间戳的抽样帧。导入使用托管副本和SHA-256去重，数据库保存处理阶段，以支持就绪内容检索与失败项重试。

**【图 RD-04：数据关系图，必须】** 绘制五张表：`assets`一对多`visual_items`，`visual_items`一对多`tags`，`assets`对应可选的`video_descriptions`和`asset_trash`记录。标出主键、外键和关键字段，不需要把所有SQL字段塞入汇报页。

**【代码 RD-05：导入与去重，必须】** 从`services/library.py:Library.import_image`或`import_video`摘录“流式读取与大小检查→哈希去重→文件落盘与登记”中的一个重点片段，建议15—25行。说明内容哈希识别完全重复文件；不宣称实现相似图片去重。完整函数作为附件供查阅。

**【界面截图 RD-06：导入结果，必须】** 使用专用样例，展示一次成功、一次重复、一次非法文件提示，保留文件名与结果对应关系。

**【附件】** `services/library.py`、`tests/test_library.py`；需要数据库样例时使用测试库，不打包用户真实素材库。

## 四、视频抽帧与时间索引

**正文：** 视频导入先校验MP4容器、H.264编码、大小及时长，再通过FFmpeg约每5秒抽样，保存实际帧时间戳。检索结果可追溯到原视频的对应时间；抽样不代表完整事件理解。

**【图 RD-08：视频时间轴示意，建议】** 用一段12秒测试视频，画出0、5、10秒三个抽样画面以及对应的视觉单元。标注“示例”，不把示意时间轴当实测数据。

**【代码 RD-09：抽帧与时间戳，必须】** 从`services/video.py:extract_video`摘录抽帧命令和时间戳处理的关键代码，解释为什么保留实际时间戳。格式校验可另放一个短片段，不需要整页FFmpeg参数。

**【日志截图 RD-10：真实抽帧结果，必须】** 运行`smoke_video.py`后截取实际抽样时间与结果；保留原始输出。截图须能识别这是FFmpeg实际执行，不使用替身测试冒充解码结果。

**【界面截图/录屏 RD-11：视频命中和定位，必须】** 展示搜索命中时间与播放器。截图只能证明展示，定位误差应以实际操作录屏或测量记录证明；未通过时标“待验收”。

## 五、语义索引与查询优化

**正文：** Jina分别编码图像和查询文本，归一化后计算相似度。查询按条件筛选兼容的向量，并合并同视频的邻近命中。查询向量缓存和矩阵计算降低重复编码及逐项计算成本，但模型首次加载仍需要等待。

**【图 RD-12：检索双路径图，必须】** 上路“图片/视频帧→图像编码→存储向量”，下路“中文查询→文本编码/缓存→查询向量”，汇合至“筛选→相似度排序→邻近合并→结果”。不要画成描述参与检索；当前描述不进入排序。

**【代码 RD-13：检索核心，必须】** 从`services/indexing.py:IndexService.search`选取向量兼容性检查、矩阵相似度计算或缓存中的关键片段；另用一句话解释`normalize`的作用。每页最多一个主要片段，避免整屏代码。

**【界面截图 RD-14：固定查询的实际结果，必须】** 截图包含查询词、筛选条件、前几个结果及相关时间信息。使用已标注的示例，不临时挑选效果最佳的查询来代替评测。

**【日志截图 RD-15：性能与模型环境，必须】** 区分首次加载、未缓存热查询、重复缓存查询，标明设备、素材规模、模型版本和计时范围。历史62.063秒、0.086秒、0.003秒只能标为历史单次诊断，不能包装为正式P95。

**【附件】** `services/embeddings.py`、`services/indexing.py`、`scripts/benchmark_search.py`、原始性能报告。正式性能评测仍待完成。

## 六、AI描述、标签与模型资源管理

**正文：** Qwen负责图片中文说明和标签，以及最多16个有序视频抽样画面的整体摘要。结果经过结构与标签校验后保存。独立进程执行描述任务，结束后退出；与检索模型互斥调度，避免同时争抢显存。描述生成后，首次新查询可能重新加载检索模型。

**【代码 RD-17：输出校验或进程管理，必须】** 从`services/captions.py:normalize_tags`及`CaptionService.describe`选择一个主片段，`services/caption_worker.py:main`作为补充。解释非法输出如何处理，不只展示提示词。

**【日志截图 RD-19：真实推理与资源，必须】** 显示本地模型、输入类型、执行结果与耗时；如展示显存，注明工具、采样时点和是否包含其他程序。只有采样值时不要写“峰值显存”。

## 九、取证命令与材料归档

以下命令用于准备证据，本文编制时未执行。工作目录为项目根目录。先确认测试环境和运行参数，模型脚本可能消耗GPU并写入测试产物。

```powershell

New-Item -ItemType Directory -Force docs/evidence/engineering

# 记录代码版本和未提交改动
git rev-parse HEAD
git status --short

# 全量回归，保留命令、错误与成功输出
.\.venv\Scripts\python.exe -m unittest discover -s tests -v 2>&1 |
    Tee-Object -FilePath docs/evidence/engineering/regression.txt

# 真实视频与向量模型冒烟：运行前查看脚本中的路径、参数和数据范围
.\.venv\Scripts\python.exe scripts/smoke_video.py
.\.venv\Scripts\python.exe scripts/smoke_embeddings.py
```

`smoke_caption.py`会对现有库中的视频生成并保存摘要，不能当成无副作用测试随意运行；应先核对脚本并选择专门测试数据。`benchmark_search.py`同样需先核对查询与素材范围。这里不提供未经验证的通用参数，也不虚构日志内容。

建议每份证据包含：编号、采集日期、代码提交及工作区状态、环境、输入样例、命令或操作、预期、实际结果、原始文件位置、采集人。失败证据可保留用于缺陷分析，但不能排版成成功结果。

推荐归档形式：

```text
docs/evidence/engineering/        # 建议目录，尚未采集
  README.md                       # 编号与证据索引
  screenshots/                    # 真实界面截图
```

图与截图统一采用紫色品牌主题，截图保留真实界面不修改结果。代码优先使用可复制的文本片段，并在页脚写文件和函数；需要截图时保留函数名及行号，裁去无关IDE区域。日志截图应保留命令、关键上下文和最终状态，隐藏个人路径或私有素材名称时用明确遮盖，不改写输出。

正式交付最低要求：源码与运行说明可定位；关键功能有真实操作证据；关键算法有可解释代码；测试有完整输出；未完成项目明确列出。图用于讲清设计，代码用于解释实现，日志和操作记录用于证明运行，三者各有用途。

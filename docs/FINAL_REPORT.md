# ObjectLift 项目完整版汇报

汇报基准：2026年11月8日。本文围绕当前产品形态组织，不按迭代版本展开。“完整版”指汇报内容完整，不表示项目所有验收已经完成。正文可作为六人讲稿底稿和后续PPT内容来源。

## 一、产品设计：我们解决什么问题

### 1. 项目定位

ObjectLift是一款面向个人创作者和学生的本地视觉素材整理与检索工具。用户导入图片和短视频后，可以生成内容描述和标签，通过中文自然语言寻找相关图片或视频画面，再预览并下载原素材。

我们关注的问题是：用户记得素材里出现过什么，却不记得文件名，也不记得相关画面位于视频的哪个时间点。传统文件夹主要依靠名称和目录组织素材，用户需要反复打开图片、拖动视频寻找内容。ObjectLift把查找入口从文件名扩展到画面内容。

例如，用户希望寻找“傍晚街道上的自行车”，可以直接输入这一描述，查看系统返回的相关图片或视频抽样画面。这个例子用于解释产品场景，正式演示前应使用固定素材验证，不能把示意场景当成已经测得的检索结果。

### 2. 用户与核心需求

| 用户场景 | 主要问题 | 产品提供的能力 |
| --- | --- | --- |
| 学生整理课程与项目素材 | 文件分散、命名不清楚 | 统一素材库、预览和文件名筛选 |
| 创作者查找图片 | 记得内容但不知道文件名 | 中文语义检索、标签筛选 |
| 查找视频中的相关画面 | 逐段播放成本高 | 抽样帧检索、命中时间与定位入口 |
| 管理已导入的素材 | 不清楚处理进度、担心误删 | 状态展示、失败重试、回收站恢复 |

上述需求是项目设计依据，当前尚无完整用户访谈或满意度评测报告，不能宣称已经证明节省多少时间。

### 3. 产品流程与范围

核心使用流程是：导入素材 → 浏览素材库 → 手动建立索引或生成描述标签 → 中文查询与筛选 → 查看详情 → 下载或管理素材。

当前面向单用户、本地Web、一个默认素材库。支持JPG/JPEG/PNG图片和限定编码的H.264 MP4视频；当前视频上限为300MB、4分钟。导入使用托管副本，不修改用户原文件。图片和视频的处理、描述生成与检索均围绕本地环境设计。

首版不包含账号、多库、模型训练、实时摄像头、音轨转写、视频片段导出和公网发布。长视频自动切片已经记录，暂不推进。

产品设计方面的工作产物包括需求文档、用户流程、功能优先级、输入限制、验收目标和范围清单。这些约束使研发可以围绕一条完整使用流程推进。

## 二、产品研发：系统如何落地

### 1. 整体架构

系统采用浏览器页面、Python服务、本地模型和本地存储的结构。界面使用Gradio，业务层负责素材导入、图片处理、视频抽帧、索引、描述生成和搜索；SQLite保存结构化信息与向量，媒体文件和模型权重分别保存在本地目录。

```text
浏览器：宣传首页 / 素材工作台
                   ↓
Python业务服务：导入、处理、索引、搜索、描述、回收站
          ↙                 ↓                  ↘
SQLite元数据与向量     托管原文件及预览图      本地图文模型
```

这个架构适合当前单用户原型：部署组件较少，数据和模型便于定位，能够直接追踪一次导入或推理失败。当前没有引入独立向量数据库、分布式队列或多服务集群。

### 2. 素材导入与持久化

导入时校验媒体，计算SHA-256以识别内容完全相同的文件，保存托管副本、元数据和预览图。损坏文件按单项报告错误，不把整个批次都判为失败。

图片处理包括方向修正、缩放、读取校验和缩略图生成。视频通过FFmpeg解码，约每5秒采样一帧，并记录实际时间戳，用于后续检索定位。固定抽样可能遗漏短暂事件，因此产品定位是画面检索，不宣称能理解视频内所有事件。

### 3. 数据结构

| 数据表 | 保存的信息 | 作用 |
| --- | --- | --- |
| assets | 原文件名称、托管路径、哈希、尺寸、时长、状态 | 表示一个原始素材 |
| visual_items | 图片或视频帧、时间戳、向量、描述及阶段状态 | 作为视觉检索和处理单元 |
| tags | 画面标签及来源 | 支持分类和筛选 |
| video_descriptions | 视频整体摘要、采样时间、模型版本与状态 | 单独保存整段摘要 |
| asset_trash | 移入回收站的素材及时间 | 支持软删除与恢复 |

把原素材与视觉单元分开后，一段视频可以对应多张抽样画面，搜索结果仍可追溯到同一个视频及其时间点。视频整体摘要单独保存，避免误当成每一帧的描述。

### 4. 状态、重试与回收站

索引和描述分别保存处理状态。未完成素材仍可浏览，只有就绪且版本兼容的向量参与检索；失败项可重试，已有有效结果可以复用。系统提供中断状态恢复机制，并通过串行调度减少模型任务之间的资源竞争。

回收站使用软删除：移入后，素材不再进入正常列表、统计、索引和搜索，但保留文件与已有索引；恢复后可重新使用。当前没有永久删除或清空回收站功能，因此不会释放磁盘空间。

研发工作产物包括业务服务、数据库结构、媒体处理、页面事件、状态恢复机制、启动脚本和自动化测试，而不只是一个调用模型的页面。

## 三、算法与模型集成：如何理解和检索素材

### 1. 两个模型的职责

| 模型 | 当前用途 | 输出 |
| --- | --- | --- |
| Jina CLIP v2 | 中文查询与图片/视频帧之间的语义匹配 | 用于相似度计算的向量 |
| Qwen2-VL-2B-Instruct | 图片描述、自动标签及视频摘要 | 可阅读的中文内容 |

Jina是图文语义检索模型，不是关键词匹配模型。它把图片和查询文字映射到可比较的向量空间。Qwen负责生成解释性内容，让用户更容易理解和分类素材。项目使用预训练模型进行本地推理，没有进行自有模型训练。

### 2. 搜索流程

入库处理时，将图片或视频抽样帧编码并保存向量。查询时，将中文文本编码为查询向量，先应用类型、标签等筛选，再计算归一化向量之间的相似度，返回排名靠前的结果。对同视频邻近时间的命中进行合并，减少相似画面重复展示。

向量需满足维度、数值和模型版本一致等约束，不能把不同模型版本的向量混合比较。相似度是排序依据，不是答案正确的概率；没有相关素材时，最近似结果也可能不符合用户需求。

### 3. 描述与标签生成

图片描述使用Qwen的图像输入，生成中文说明和最多5个粗粒度标签。标签覆盖人物、动物、建筑、自然、室内、交通、食物和物品等预设类别，生成结果经过结构和类别校验，并支持未分类状态。

视频摘要从已有抽样画面中选取最多16帧，按时间顺序联合生成，描述基于画面，不包含音轨信息。这是视频整体摘要，当前尚未完成每个视频帧的描述和标签生成。

当前支持单项生成以及未完成/失败图片的批量补齐；导入后不会自动启动完整处理链路。

### 4. 为什么不只搜索描述

“先生成描述，再检索描述”是一条可行的替代路线。但描述会压缩视觉信息，例如画面里的红伞没有被写入描述，后续仅搜索描述就可能漏掉它。描述生成错误也会影响检索依据。若要对描述做语义搜索，仍需要文本向量编码或其他语义匹配机制。

当前采用直接图文检索作为主线，描述用于展示、标签用于筛选；描述没有参与向量计算和搜索排序。后续计划使用同一套素材与查询，对比直接图文检索和描述检索，再判断是否需要融合。该对比尚未实施，不能宣称双模型已经证明优于单模型。

### 5. 资源与性能工程

项目针对RTX 5060 Laptop 8GB环境完成过真实推理验证。采用固定模型版本、本地加载、模型任务串行和独立描述进程，生成结束后退出进程释放其资源；描述生成会与检索模型使用互斥机制，之后首次新查询可能重新加载检索模型。

查询侧增加向量缓存、矩阵相似度计算和预热入口。冷启动与热查询分开记录，避免用已缓存查询的耗时代表所有用户操作。这部分工作包括依赖兼容、模型代码与配置检查、设备适配、输出校验、资源管理和性能诊断。

## 四、交互与视觉设计：让能力变得可用

### 1. 信息组织

系统提供品牌宣传首页和素材工作台。首页解释产品用途并引导进入工作台；工作台采用顶部搜索、左侧类型/标签/文件名筛选、中间素材网格、右侧预览详情的布局。

用户没有查询词时，可以浏览素材；输入中文查询后查看相关结果。详情区集中展示预览、文件信息、描述、标签、状态与下载入口，减少来回切换。

### 2. 处理反馈

模型生成需要等待，界面显示加载或生成阶段、等待时间和批量进度，并在执行期间禁用相关生成按钮。失败后显示错误与重试入口，避免用户反复点击或把未处理完成的素材误认为已经可检索。

导入和处理操作收纳在对应区域，诊断信息放入独立区域。AI描述与实际画面共同展示，用户可以核对生成内容，而不是只看到模型结论。

### 3. 操作闭环

工作台覆盖浏览、查询、筛选、查看详情、下载、移入回收站和恢复。视频搜索展示命中帧和时间，并提供播放器定位入口；定位误差仍需浏览器正式验收。窄屏布局采用纵向堆叠，设备适配仍待实测。

交互与视觉方面的产物包括首页、品牌图标、工作台布局、状态文案、反馈与错误提示、素材详情和回收站界面。汇报时可用实际截图展示这些设计如何帮助用户完成任务，不需要逐个介绍所有按钮。

## 五、测试与质量保障：我们如何证明有效

### 1. 三层验证

| 验证层次 | 检查什么 | 能证明什么 |
| --- | --- | --- |
| 自动化回归 | 去重、状态、持久化、失败隔离、筛选、重试和恢复 | 业务逻辑在测试条件下符合预期 |
| 真实模型与媒体冒烟 | 实际模型加载、图片/视频输入、生成与检索 | 指定样本的真实链路能够运行 |
| 浏览器与质量验收 | 页面操作、视频定位、结果相关性、用户体验 | 面向使用场景的可用性与效果 |

使用替身编码器的测试不能代替真实模型验收；接口返回成功不能代替浏览器交互通过；单个样本生成成功也不能证明模型普遍准确。

### 2. 已有验证证据

| 项目 | 历史记录结果 | 适用边界 |
| --- | --- | --- |
| 自动化回归 | 开发日志最后记录27项通过 | 本次整理没有重新获得全量通过结果 |
| 真实视频抽帧 | 12秒H.264测试视频产出0、5、10秒三帧 | 不代表所有编码和长视频都通过 |
| 搜索耗时 | 一次诊断：冷查询62.063秒、新热查询0.086秒、重复查询0.003秒 | 不含浏览器渲染，不是P95或大规模性能报告 |
| 视频摘要 | 206.464秒视频两次真实推理15.261秒、12.305秒 | 含子进程加载，基于16个抽样画面，不是摘要准确率评测 |
| 图片描述 | 莲花花蕾图片完成真实描述与标签生成 | 单样本验证 |
| 页面检查 | 首页进入工作台、22项素材加载、点击图片更新预览与下载记录正常 | 不等于所有浏览器流程验收完毕 |

这些数字来自开发记录，正式汇报需保留测试条件和口径。冷启动仍是明显的体验问题，不能只展示毫秒级缓存查询。

### 3. 尚未完成的验收

计划使用100张图片、5段短视频建立固定测试集，准备20条相关查询与5条无相关查询，并提前标注相关素材和视频时间区间。素材规模是验收计划，不是已经完成的实验。

主要目标为：Top-5命中率≥80%；模型已加载、1000检索单元条件下热查询P95≤3秒；浏览器视频跳转误差≤1秒。这些是目标，目前不能写成实测结论。

还需覆盖损坏文件、任务中断、重试、恢复、完整浏览器操作和备份恢复。模型可能遗漏细节、推测内容，固定抽帧可能漏掉短事件，这些应在评测和展示中保留原画面供核实。

### 3. 风险与下一步

| 风险或缺口 | 后续处理 |
| --- | --- |
| 检索质量尚无统一证据 | 建立固定查询与标注集，先评测现有图文检索 |
| 两种检索路线尚未对照 | 对比描述检索，依据结果决定是否融合 |
| 导入后的处理仍需手动触发 | 明确自动处理范围和资源调度后再实现 |
| 视频定位与逐帧整理范围不完整 | 完成定位验收，明确逐帧描述是否纳入交付 |
| 冷启动和模型切换影响等待 | 分别记录耗时，完善预热及状态反馈 |
| 容器不能直接代表本机能力 | 补齐依赖并实测GPU推理、持久化和恢复 |
| 文档存在旧状态 | 按当前代码和实际测试更新说明与验收表 |

推进顺序建议为：同步验收状态 → 准备固定素材和查询 → 评测检索质量 → 根据结果确定检索路线 → 完成浏览器及异常验收 → 完成Docker与备份恢复 → 冻结演示版本。

长视频切片、永久删除和回收站清空保持后续需求，避免挤占核心验收时间。

### 4. 结束陈述

ObjectLift已经把本地素材管理、图文语义检索、视频抽样定位、AI内容说明和可恢复管理结合成一个可运行原型。项目工作覆盖需求设计、业务研发、模型适配、用户交互、质量验证和工程交付。下一阶段的重点是用固定评测与完整验收，确认现有功能在真实使用场景下的效果，并完成可复现的交付。

# ObjectLift 三轮迭代汇报与六人分工

汇报基准：2026-11-08。建议总时长18分钟，每人约3分钟，共18页；如课程另有限时，可按比例压缩。

本文按开发过程划分“汇报版 V1/V2/V3”，不是仓库正式发布标签。日志日期与提交日期可能不同，以开发日志说明过程、Git提交辅助追溯。人员编号代表建议的汇报职责，不代表已核实的历史贡献；正式汇报时补入姓名和真实参与工作，避免把讲述分工当成开发贡献。

## 一、汇报主线

ObjectLift 从“图片转3D素材”的探索起步，先完成图片处理和Web原型。在模型获取、环境验证与一周交付约束下，团队重新确定为本地视觉素材整理与检索工具，随后完成素材库、中文图文检索和视频抽帧，再补充AI描述、分类、工作台体验与回收站。

目前交付的是可运行的本地原型。主要功能已经形成闭环，真实模型链路有验证记录；固定查询集质量评测、完整浏览器验收和Docker GPU交付仍未完成。

汇报必须体现六个方面：产品设计、产品研发、算法与模型集成、交互与视觉设计、测试与质量保障、项目管理与交付。每个方面讲清“问题—工作—产物—验证—不足”，不以代码行数代替工作量。

## 二、三个迭代版本

### V1：方向探索与图片处理原型

阶段：2026-11-06早期探索。目标是验证图片素材处理链路，为图片转3D方案评估可行性。

**产品设计工作**：定义学生、游戏原型开发者和内容创作者场景；设计上传、目标选择、前景确认、生成与导出流程；明确单物体、单用户、不训练模型等边界。

**研发工作**：实现图片读取、EXIF方向修正、缩放、裁剪、透明通道和空前景校验；建立独立任务目录和处理记录；实现Web上传、裁剪及PNG/JSON下载，修改上游输入后清理旧下游状态。

**验证与探索**：检查Windows/WSL GPU和Docker引擎；尝试获取TripoSR源码与依赖；解决Pillow和Gradio版本兼容问题。日志记录图片处理8项测试通过，Web阶段11项测试通过，并完成上传到裁剪下载的接口冒烟验证。

**实际交付**：图片处理模块、旧版四步工作台、任务隔离机制、启动脚本、初版容器配置及早期PRD。

**未完成边界**：自动目标检测、自动去背景和真实3D生成没有完成；透明前景校验不等于自动去背景，页面预留按钮不等于功能可用。

**迭代决策**：源码下载与容器验证受阻，真实3D效果没有形成证据。结合短周期约束，暂停3D方向，保留图片处理基础，转向视觉素材管理和检索。该阶段应作为技术探索与范围调整汇报，不能包装成完整3D产品。

### V2：本地素材库与中文语义检索

阶段：2026-11-06至11-07。目标从“生成新素材”调整为“整理并找回已有素材”。

**产品设计工作**：重写PRD与技术路线，确定单用户、本地Web、默认素材库；设计图片和短视频统一浏览、自然语言搜索、命中画面预览与原文件下载。

**研发工作**：用SQLite保存素材、画面、标签与向量；托管导入副本，以SHA-256去重；实现缩略图、逐文件错误隔离、索引状态及重试。接入H.264 MP4，约每5秒抽帧，保存实际时间戳；提供类型筛选、相邻视频命中合并及定位入口。视频上限调整到300MB/4分钟。

**模型集成工作**：接入本地Jina图文向量模型，固定模型及代码版本，校验向量维度与归一化，隔离不同模型版本；从CPU验证推进到RTX 5060 GPU实测。

**性能工作**：增加查询向量缓存、矩阵相似度计算和搜索预热，避免改变筛选条件时重复编码；将模型任务串行处理，提供繁忙提示。

**验证证据**：阶段回归由13项增至21项；真实FFmpeg对12秒测试视频产出0、5、10秒三帧。日志中的一次本地搜索诊断记录冷查询62.063秒、后续新查询0.086秒、重复查询0.003秒；这些是单次服务端数据，不代表P95或浏览器端耗时。

**实际交付**：可以导入、保存、索引和检索图片/视频画面的本地素材库。

**遗留问题**：自动描述尚需补齐；检索相关性未完成固定查询集评测；播放器入口存在，但浏览器定位误差尚未正式验收；模型冷启动较慢。

### V3：AI整理、工作台完善与可恢复管理

阶段：2026-11-07至11-08。目标是让素材更容易理解、分类和管理，改善使用体验。

**模型与业务工作**：接入Qwen2-VL-2B，生成基于最多16个有序抽样画面的视频整体摘要；接入图片中文描述、粗粒度自动标签及标签筛选，校验输出结构。通过独立推理进程、模型任务串行、状态持久化与失败重试控制资源和异常。

**交互工作**：提供单项生成、未完成/失败图片批量补齐、未分类处理，以及生成阶段和等待时长反馈。工作台调整为顶部搜索、左侧筛选、中间素材网格、右侧预览详情；诊断移到独立区域，支持无查询浏览。

**视觉与管理工作**：制作ObjectLift品牌图标和宣传首页，首页进入工作台；增加回收站和恢复，确保搜索、统计和索引排除回收站素材，同时保留原文件和已有索引。

**验证证据**：206.464秒视频两次真实摘要推理耗时15.261秒和12.305秒，包含子进程加载；一张莲花花蕾图片完成真实描述和标签生成。日志记录首页及工作台22项素材加载、图片点击预览正常，最终27项回归通过。单样本推理成功不等于分类或描述准确率达标。

**实际交付**：包含首页、素材工作台、语义检索、AI描述/标签和回收站的本地原型。

**遗留问题**：导入后自动处理尚未启用；视频整体摘要不等于逐帧描述和标签；永久删除及空间释放未实现；长视频切片已记录但暂缓；完整浏览器验收、质量评测及新版Docker GPU验证仍待完成。

## 三、技术路线说明：为什么使用两个模型

当前路线：查询文字 → Jina文本向量；图片/视频帧 → Jina图像向量；比较相似度返回素材。Qwen负责生成描述和标签，标签参与筛选，描述当前没有参与搜索排序。

Jina不能称为“关键词检索模型”。它负责图文语义匹配；Qwen负责生成可读的内容说明。两者能力有交集，当前职责不同。

备选路线是“图片 → Qwen描述 → 描述文本检索”。该路线可行，但语义检索仍需要文本编码或其他语义匹配机制；描述遗漏的视觉细节可能无法找回。视频整体摘要也无法单独提供准确的画面时间定位。

建议后续在相同素材与查询集上比较直接图文检索、描述文本检索，再决定是否融合。该比较尚未实施，不宣称双模型已经证明优于单模型，也不宣称已实现混合检索。

## 六、现场演示安排

建议由同学5统一操作，控制在90秒内，计入其3分钟。使用来源清楚、可公开展示的样例素材，提前完成索引并预热检索模型。

1. 从首页进入工作台，展示素材库和类型筛选。
2. 输入预先固定的中文查询，展示相关图片与详情。
3. 展示已生成的AI描述、标签和筛选结果，明确是预先生成的结果。
4. 若视频定位预演通过，展示命中帧和播放器跳转；否则展示时间戳并说明定位验收待完成。
5. 使用专门的演示素材展示移入回收站和恢复，说明不会释放磁盘空间。

不要现场等待大模型首次加载或批量生成。可准备一段真实录屏作为失败备用，并标明录制时间；截图、录屏需在汇报前实际采集，本文不代表已经准备好。

### 后续开发顺序

1. 同步文档与代码状态：修正“图片描述未实现”“没有批量补齐”等过时说明，逐项更新验收表。
2. 建立固定素材与查询集：目标100张图片、5段视频、20条相关查询和5条无相关查询；这是计划规模，不是已有评测成果。
3. 评测当前图文检索：Top-5命中率目标≥80%，热查询P95目标≤3秒；明确素材、人工相关标注、模型版本和计时范围。
4. 按结果决定是否接入描述检索，明确导入自动处理和视频逐帧标签是否纳入本轮。
5. 完成浏览器全流程及异常验收，验证视频定位误差目标≤1秒。
6. 升级并验证Docker GPU环境，实测数据持久化和备份恢复，再冻结演示版本。

长视频自动切片、永久删除和清空回收站作为后续需求，不挤占核心验收。3D仍保持暂停。

## 八、统一汇报口径与证据索引

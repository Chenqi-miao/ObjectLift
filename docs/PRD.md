**项目确定为：从图片中发现、选择物体，再生成可下载的 3D 素材。** 一周先交付图片版，视频选帧作为扩展。第一天先验证 TripoSR 在你们的 5060 8GB 上能生成模型，再全面展开开发。

以下方案可以作为团队 PRD，也可以拆给不同 AI 开工。

---

## 1. 项目定义

**项目名称：ObjectLift——基于目标检测与单图重建的 3D 素材生成工具**

**一句话定位：** 上传照片，自动找到其中的常见物体，点选并去除背景，生成可交互查看、可下载的 3D 模型。

**目标用户：** 需要快速制作原型素材的学生、游戏开发者、3D 内容创作者。

**典型场景：** 用户拍到一张包含狗、椅子和人的照片，系统检测并编号；用户选择狗，检查去背景效果后生成 3D 模型，旋转预览并下载，作为后续创作初稿。

**产品边界：**

- 检测范围以通用 YOLO 模型支持的类别为准。
- 一次生成一个目标，输出单体模型。
- 单图无法确定背面和遮挡部分，生成结果是推测的形状。
- 不恢复真实尺寸，不保证拓扑适合动画或直接用于生产。
- 不训练模型，不生成完整场景，不要求实时处理。

## 2. 核心流程与 AI 的作用

```text
上传图片
   ↓
YOLO 检测物体
   ↓
用户选择目标 → 裁剪并保留适当边距
   ↓
去背景 → 用户检查透明预览
   ↓
TripoSR 生成单体网格
   ↓
3D 预览 → 下载模型和处理结果
```

| 模块 | 作用 | 输出 |
|---|---|---|
| 目标检测 | 在复杂图片中发现可选物体 | 类别、框、置信度、编号 |
| 去背景 | 提取选中物体，减少背景干扰 | 透明 PNG |
| 3D 重建 | 从单张前景图推测立体形状 | 网格及顶点颜色 |
| 产品交互 | 让用户选择、检查、重试和导出 | 可追溯的处理任务 |

**检测用于批量发现候选目标；用户还可以手动裁剪补充。** 这样即使物体不在检测类别中，也能继续尝试生成。

## 3. 一周 MVP 功能

| 优先级 | 功能 | 验收标准 |
|---|---|---|
| P0 | 图片上传 | 支持 JPG、PNG，正确处理 EXIF 方向、透明背景和损坏文件 |
| P0 | 自动检测 | 展示框、类别、置信度及稳定编号，阈值可调 |
| P0 | 目标选择 | 从候选列表选择对象，显示裁剪预览 |
| P0 | 裁剪调整 | 支持调整裁剪范围，避免切掉尾巴、椅腿等部位 |
| P0 | 去背景 | 展示透明前景；允许上传用户自行处理的透明 PNG |
| P0 | 3D 生成 | 一次一个任务，显示处理阶段，失败可重试 |
| P0 | 3D 查看 | 浏览器中旋转、缩放生成模型 |
| P0 | 下载 | 下载 GLB、透明 PNG、结果说明 JSON |
| P0 | 异常处理 | 无目标、空前景、模型加载失败、显存不足均有提示 |
| P1 | 示例素材 | 提供数张经过实测、来源许可明确的示例 |
| P1 | 视频选帧 | 抽帧检测，用户选一帧进入相同生成流程 |
| P1 | 多候选帧推荐 | 按目标大小、清晰度等规则辅助选图 |

**本周不做：** 多对象同时生成、视频多视角融合、自动骨骼绑定、高质量贴图烘焙、完整场景重建、账户系统和云服务部署。

首版默认使用 **TripoSR 的顶点颜色输出**。GLB 导出需实际检查颜色保留，不提前承诺精细纹理效果。

## 4. 页面设计与演示

界面分成四步，避免用户上传图片后直接面对一堆参数。

| 步骤 | 页面内容 | 主操作 |
|---|---|---|
| ① 找物体 | 上传区、检测参数、带框结果、候选列表 | 检测并选择 |
| ② 提取物体 | 裁剪预览、裁剪调整、透明前景预览 | 去背景、确认前景 |
| ③ 生成模型 | 输入缩略图、处理阶段、错误与重试入口 | 生成 3D |
| ④ 查看导出 | 3D 视图、任务摘要、下载按钮 | 旋转查看、下载 |

必须有的交互规则：

- 上传新图片后，清除旧检测、前景和模型结果。
- 换选目标后，旧的前景与模型失效。
- 修改前景后，需要重新生成模型。
- 生成期间禁止重复提交；同一时间只运行一个生成任务。
- 没检测到目标时，可手动裁剪或直接上传单物体透明图。
- 去背景失败时，保留裁剪图，让用户调整或替换输入。

**三分钟答辩演示：**

1. 上传包含多个物体的照片，展示自动检测和编号。
2. 选择一个目标，调整裁剪，查看去背景结果。
3. 提交生成，说明各阶段作用。
4. 旋转模型，展示侧面和背面，同时解释它们是估计结果。
5. 下载 GLB，重新打开验证。
6. 若实测生成较慢，现场提交任务，同时展示明确标记的历史生成结果。

## 5. 技术方案与显存安排

| 层次 | 技术 |
|---|---|
| 运行环境 | Python，具体版本由 TripoSR 安装验证后统一 |
| 界面 | Gradio |
| 检测 | Ultralytics YOLO11n 通用预训练权重 |
| 图像处理 | Pillow、NumPy |
| 去背景 | `rembg` 作为首选候选，先在真实目标上验证 |
| 单图重建 | TripoSR |
| 网格处理与导出 | trimesh |
| 测试 | Pytest |
| 协作与发布 | Git、GitHub Issues、Pull Request、GitHub Actions |

**不再使用 Depth Anything。** 当前输出单个物体，不需要计算它在原照片中的三维位置。

TripoSR 官方给出的默认单图显存需求约为 **6GB**，你们的 8GB 显卡具备试跑条件；Windows 扩展安装和真实峰值占用仍需验证。[TripoSR 官方说明](https://github.com/VAST-AI-Research/TripoSR)

采用以下资源策略：

- YOLO 优先放 CPU，先保证生成阶段显存充足。
- 去背景优先使用 CPU。
- GPU 主要供 TripoSR 使用，一次处理一个目标。
- 若检测使用 GPU，生成前真正释放检测模型占用；单纯调用显存缓存清理不等于卸载模型。
- 生成任务优先隔离到独立进程，失败后便于释放 GPU 资源。
- 模型下载、首次加载、推理和网格导出分别记录耗时。
- 不承诺具体秒数，以本机实测为准。

**安装策略：** 先尝试一个独立生成环境；如果 TripoSR 与检测依赖冲突，就将“应用环境”和“生成环境”分开，通过子进程和文件契约调用。

## 6. 系统结构与共享接口

```text
objectlift/
├── app.py
├── schemas.py
├── config.py
├── services/
│   ├── image_io.py
│   ├── detector.py
│   ├── foreground.py
│   ├── generation_client.py
│   ├── exporter.py
│   └── pipeline.py
├── workers/
│   └── triposr_worker.py
├── ui/
│   └── page.py
├── tests/
├── scripts/
├── docs/
├── requirements-app.txt
└── requirements-generation.txt
```

每个任务使用独立目录，避免用户之间或多次提交之间覆盖文件：

```text
jobs/<job_id>/
├── input.png
├── detections.json
├── crop.png
├── foreground.png
├── model.glb
├── manifest.json
└── worker.log
```

共享数据契约先冻结：

```python
Detection:
    id: str
    class_id: int
    label: str
    confidence: float
    bbox_xyxy: tuple[float, float, float, float]

GenerationRequest:
    job_id: str
    foreground_path: str
    output_dir: str
    preset: str               # 首版仅提供经过验证的预设

GenerationResult:
    job_id: str
    status: str               # succeeded / failed
    model_path: str | None
    timings_ms: dict
    warnings: list[str]
    error_code: str | None
```

模块入口：

```python
load_image(path) -> Image

detect(image, confidence) -> list[Detection]

crop_target(image, bbox, padding_ratio) -> Image

remove_background(crop) -> Image  # RGBA

generate(request) -> GenerationResult

export_manifest(job_id, metadata) -> str
```

约定：

- 所有检测框都对应同一张经过方向修正的处理图片。
- 传给生成器的前景必须经过验证：尺寸有效、存在非透明像素。
- 前景缩放、居中、背景合成等预处理遵循 TripoSR 的实际输入要求，避免重复处理。
- `manifest.json` 记录模型版本、参数、目标信息、耗时、警告和输出文件。
- 输入图片、裁剪图、前景与生成模型建立关联，能够追溯。
- 仅在生成成功且模型通过基本检查后显示下载入口。

## 9. 测试与验收标准

| 层次 | 检查内容 |
|---|---|
| 单元测试 | 图片方向、框裁剪越界、透明图检查、状态转换、错误解析 |
| 集成测试 | 使用替身验证完整流水线；使用真实模型验证端到端结果 |
| 文件检查 | GLB 可重新加载，包含有效网格，颜色保留情况正确记录 |
| 异常测试 | 损坏图片、无目标、空前景、生成进程失败、超时、重复提交 |
| 资源测试 | 连续任务、CPU/GPU占用、显存回收、临时文件清理 |
| 用户验收 | 选择正确对象、结果不串图、预览可用、下载可打开 |

生成效果单独评估，选取不同输入：

- 轮廓完整、背景简单的物体。
- 多目标但遮挡少的照片。
- 毛发、细腿、遮挡等困难样例。

记录“是否生成成功、主体是否可辨认、是否有缺失或粘连、处理时间”。**不把“成功输出文件”当成“模型质量合格”。**

## 10. 给各 AI 的开工提示词

先把本方案的第 1–6 节发给所有 AI，再分别追加下列提示词。

**1：产品与 QA**

> 你是 ObjectLift 的产品经理兼 QA。请依据已冻结范围，创建用户故事、验收清单、手工测试用例、Bug 模板和三分钟演示脚本。覆盖成功路径、无目标、去背景失败、生成失败、状态串图和文件导出。维护需求编号与测试用例对应关系。性能数据必须来自实测，预生成结果必须标记。不要增加视频等 P1 功能。

**2：检测模块**

> 你负责 image_io.py、detector.py 和对应测试。实现方向修正、RGB 处理、尺寸限制、YOLO11n 检测、稳定编号、带框预览、带边距裁剪和坐标映射。优先 CPU 推理。遵守共享接口，不修改 UI 和生成模块。支持用替身运行测试，真实模型测试独立标记。交付可运行代码、模块说明和验证结果。

**3：前景模块**

> 你负责 foreground.py 和对应测试。先验证 rembg 对真实物体的效果，实现透明前景输出、有效前景检查、输入规范化与错误提示。允许用户提供透明 PNG 替换自动结果。检查狗的毛发、细腿及邻近目标残留，明确自动去背景不一定能分离多个紧邻物体。与 3D 工程师统一预处理，只执行一次必要的居中、缩放与背景合成。

**4：3D 生成模块**

> 你负责 TripoSR 真机验证、生成环境和 triposr_worker.py。设备为 RTX 5060 8GB、内存32GB、Windows。第一任务是生成并打开真实网格，记录环境、耗时与显存。按共享文件协议封装独立进程，一次一个任务，处理失败和退出码。首版采用默认网格与顶点颜色，不加纹理烘焙。验证 GLB 转换和颜色保留。不要虚构测试结果，跑不通时优先定位依赖和显存问题。

**5：界面模块**

> 你负责 ui/page.py。使用 Gradio 实现上传检测、目标选择与裁剪、前景确认、生成预览与下载四步流程。先用 Mock 开发，再接真实接口。使用会话状态；输入或目标变化后清除下游旧结果。生成期间禁止重复提交。展示阶段状态、可读错误、历史结果标记和模型局限。不要把终端堆栈直接显示给用户，不开启公开分享。

**6：系统集成与发布**

> 你负责 schemas.py、config.py、pipeline.py、generation_client.py、exporter.py、app.py、依赖文件、CI与启动脚本。先发布共享契约和 Mock，再组织其他模块接入。为每个任务建立独立目录，通过子进程调用生成 worker，支持超时终止和错误归类。记录 manifest，检查下载文件。CI不下载模型；真实模型测试另行执行。完成 Windows 安装验证、模型缓存说明、临时文件清理方式和可复现发布文档。

**现在第一批任务就发给 3D 工程师做硬件验证，其余人同步完成接口、Mock、检测和去背景。Day 1 验证通过后，按这份范围推进，不再增加新的模型或产品方向。**
